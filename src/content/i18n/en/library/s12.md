Prop drilling is passing a prop through several levels of components that do not need it themselves. There are two cures for it: composition through `children`, and Context, which delivers a value straight to the descendants that need it.

### In simple words

Prop drilling is like a note passed through the whole class: every pupil passes it to the neighbour without reading it. Context is like an announcement over the loudspeaker: everyone who needs it hears it, and nobody has to work as a postman.

### Terms of the section

| Term | Strict definition | In simple words |
| --- | --- | --- |
| Prop drilling | Passing a prop through intermediate components that only forward it | A note passed through the whole class |
| Context | A React mechanism for passing a value to all descendants without explicit props | A loudspeaker for the whole subtree |
| `createContext` | A function that creates a context object with a default value | Setting up a “radio station” |
| Provider | A component that sets the value of a context for everything inside it | A transmitter: “I broadcast for everyone inside me” |
| `useContext` and `use` | Hooks that read the value of the nearest provider up the tree | A receiver: “tune in to the station” |
| Global state | Data needed by many parts of the app at once | A shared notice board |

### The problem on an example: the user’s role in the fridge

The “Smart Fridge” has the roles ADMIN, USER and GUEST. Only the administrator should see the “Delete” button, and the product card deep down the tree decides it.

```jsx
function App() {
  const user = { name: 'Alexey', role: 'ADMIN' };
  return <FridgePage user={user} products={products} />;
}

function FridgePage({ user, products }) {
  // FridgePage does not need the role — it only forwards user further
  return <ProductList user={user} products={products} />;
}

function ProductList({ user, products }) {
  // and ProductList only forwards it too
  return <ul>{products.map((p) => <ProductCard key={p.id} product={p} user={user} />)}</ul>;
}

function ProductCard({ product, user }) {
  const canDelete = user.role === 'ADMIN'; // and only here is user finally needed
  return <li>{product.name}{canDelete && <button>Delete</button>}</li>;
}
```

Why this is bad:

- The intermediate components know about data they do not need, and they are harder to reuse.
- A new field for the card forces you to edit every level along the way.
- The deeper the tree, the longer the forwarding chain.

::diagram drilling

The provider makes `user` available to the whole subtree: `ProductCard` reads it through `useContext`, and the intermediate components no longer need to pass it down the chain.

### Cure 1: composition

The React documentation advises trying ordinary props or passing JSX through `children` first, and only then reaching for context ([source](https://react.dev/learn/passing-data-deeply-with-context)). If `FridgePage` is just the frame of a page, let it accept content, and let the list be created by `App`, which already has `user`:

```jsx
function App() {
  const user = { name: 'Alexey', role: 'ADMIN' };
  return (
    <FridgePage title="My fridge">
      <ProductList user={user} products={products} /> {/* we create it where the data already is */}
    </FridgePage>
  );
}

// Now FridgePage knows nothing about the user
function FridgePage({ title, children }) {
  return (
    <section>
      <h1>{title}</h1>
      {children}
    </section>
  );
}
```

One extra level of forwarding is gone. Often that is already enough.

### Cure 2: Context

```jsx
import { createContext, useContext, useState } from 'react';

// 1. We create a context. The default value is a guest, as in the rules of your app
export const UserContext = createContext({ name: 'Guest', role: 'GUEST' });

// 2. The provider: everything inside <UserContext> sees user
function App() {
  const [user] = useState({ name: 'Alexey', role: 'ADMIN' });
  return (
    <UserContext value={user}>
      <FridgePage products={products} /> {/* we no longer pass user */}
    </UserContext>
  );
}

function FridgePage({ products }) {
  return <ProductList products={products} />;
}

function ProductList({ products }) {
  return <ul>{products.map((p) => <ProductCard key={p.id} product={p} />)}</ul>;
}

// 3. The consumer: reads the value directly, bypassing the intermediate levels
function ProductCard({ product }) {
  const user = useContext(UserContext);
  const canDelete = user.role === 'ADMIN';
  return <li>{product.name}{canDelete && <button>Delete</button>}</li>;
}
```

What the test run on React 19.3.1 showed:

| Situation | Result |
| --- | --- |
| `<UserContext value={user}>` with the ADMIN role | Every product has a “Delete” button |
| There is no provider above | The default value GUEST works, there are no buttons |
| The old notation `<UserContext.Provider value={…}>` | Works too |
| Two nested providers | The component reads the nearest one above |
| `use(UserContext)` instead of `useContext` | Works the same way |

The notation `<UserContext value={…}>` without `.Provider` appeared in React 19. In articles and old code you will more often see `.Provider` — both variants do the same thing.

### When to choose what

| Situation | Tool |
| --- | --- |
| The data is needed by a child or a grandchild | Ordinary props |
| The intermediate components are just frames and layouts | Composition through `children` |
| A value is needed by many components at different levels: the theme, the language, the current user | Context |
| A big shared state that changes often | Context + `useReducer` or a separate state library |

### Cautions with Context

- All the components that read a context re-render when its value changes. `memo` does not save you from this.
- A new object in `value` on every render makes all the readers re-render. Keep the value in state or wrap it in `useMemo`, as in section 10.
- Context makes the data flow less visible: the props of a component no longer show what it depends on. That is why context is a tool for truly shared data, not a replacement for any props.
