JavaScript itself does not check that a value of the right type came into a prop: `quantity="2"` instead of a number passes silently. Today props are described with TypeScript types or JSDoc comments, and the editor catches the mistake before anything runs. The old way, `propTypes`, was removed in React 19.

### In simple words

A type description is a contract between the parent and the child: “I accept `name` — a string, `quantity` — a number, `onDelete` — a function that gets an id”. If the contract is broken, the editor underlines the mistake at once. It is like the shape of a plug and a socket: a plug that does not fit simply cannot be inserted.

### Terms of the section

| Term | Strict definition | In simple words |
| --- | --- | --- |
| Type | A description of the set of allowed values | “What may be put here” |
| TypeScript | An add-on over JavaScript with static types; before running the code is turned into ordinary JS | JavaScript with a “spelling” check of the data |
| Static checking | Finding mistakes in the text of a program without running it | Checking homework before handing it in, not at the exam |
| Props type | A description of the shape of the props object: which fields and of which types | A form: which fields there are and what to write in them |
| Optional prop | A prop marked with the `?` sign; it may be left out | An “optional” field of a form |
| Union type | The type “one of the listed values” | A choice from a drop-down list |
| JSDoc | `/** … */` comments with type descriptions in ordinary JavaScript | Types in comments, without moving to TypeScript |
| PropTypes | An outdated check of props while the program runs | The old inspector that React 19 switched off |

### TypeScript: the props of a product card

```tsx
// ProductCard.tsx
import type { ReactNode } from 'react';

// The roles from the “Smart Fridge”: only one of three strings is allowed
export type Role = 'ADMIN' | 'USER' | 'GUEST';

export type Product = {
  id: number;
  name: string;
  quantity: number;
  expiryDate?: string; // an optional field
};

type ProductCardProps = {
  product: Product;
  canDelete?: boolean;            // an optional prop
  onDelete: (id: number) => void; // a function: it gets a number, the result does not matter
  children?: ReactNode;           // any content between the tags
};

export function ProductCard({ product, canDelete = false, onDelete, children }: ProductCardProps) {
  return (
    <li>
      {product.name} — {product.quantity} pcs
      {children}
      {canDelete && <button onClick={() => onDelete(product.id)}>Delete</button>}
    </li>
  );
}
```

The notations one by one:

- `type ProductCardProps = { … }` describes the shape of the props. After the colon in the parameters (`}: ProductCardProps`) we say: “the props must be like this”.
- `canDelete?: boolean` — the `?` sign makes the prop optional, and `= false` in the parameters sets the default value.
- `(id: number) => void` is the type of a function. `void` means “returns nothing useful”.
- `ReactNode` is the type “anything React can draw”, from section 8.
- `Role` is a union type: the compiler will not let a typo in the name of a role pass.

### What mistakes TypeScript catches

The examples were run through the TypeScript 7.0.2 compiler. Here is what it said about the wrong code:

| Wrong code | The compiler’s message | Meaning |
| --- | --- | --- |
| `<ProductCard product={milk} />` | `Property 'onDelete' is missing in type '{ product: Product; }' but required in type 'ProductCardProps'.` | A required prop was forgotten |
| `quantity: '10'` in the product object | `Type 'string' is not assignable to type 'number'.` | A string instead of a number |
| `onDelete={(id) => id.toUpperCase()}` | `Property 'toUpperCase' does not exist on type 'number'.` | `id` is a number, and a number has no such method |
| `const role: Role = 'MODERATOR'` | `Type '"MODERATOR"' is not assignable to type 'Role'.` | There is no such role |

### The props of HTML elements: ComponentProps

To avoid rewriting all the attributes of a button by hand, you take the ready type `ComponentProps<'button'>` and add your own props to it:

```tsx
import type { ComponentProps } from 'react';

// All the attributes of <button> plus our own variant
type FridgeButtonProps = ComponentProps<'button'> & {
  variant?: 'primary' | 'danger';
};

export function FridgeButton({ variant = 'primary', ...rest }: FridgeButtonProps) {
  return <button className={`btn btn-${variant}`} {...rest} />;
}

// In React 19 the type ComponentProps<'input'> already contains ref
export function SearchInput({ ref, ...rest }: ComponentProps<'input'>) {
  return <input ref={ref} className="search-input" {...rest} />;
}
```

On `<FridgeButton variant="warning">` the compiler answered that the type `"warning"` cannot be assigned to a prop that allows only `"primary"` and `"danger"`. Both components passed the check without errors.

### Without TypeScript: JSDoc in an ordinary .js or .jsx

If the project is in ordinary JavaScript, the types can be written in comments. The line `// @ts-check` at the start of the file turns on the check in VS Code.

```jsx
// @ts-check

/**
 * A product card.
 * @param {{
 *   product: { id: number, name: string, quantity: number },
 *   canDelete?: boolean,
 *   onDelete: (id: number) => void
 * }} props
 */
export function ProductCard({ product, canDelete = false, onDelete }) {
  return (
    <li>
      {product.name}
      {canDelete && <button onClick={() => onDelete(product.id)}>Delete</button>}
    </li>
  );
}
```

The same compiler checked this file too. On `quantity: '2'` it gave the same error “Type 'string' is not assignable to type 'number'”, although the file stayed ordinary JavaScript.

### PropTypes and defaultProps: what changed in React 19

| Mechanism | Before React 19 | In React 19 | What to replace it with |
| --- | --- | --- | --- |
| `Component.propTypes` | Warnings in the console in development mode | Removed: the checks are silently ignored | TypeScript or JSDoc |
| `defaultProps` of a function | Worked | Removed: the value is not substituted | Default values in destructuring |
| `static defaultProps` of a class | Worked | Works | Can stay |

All three rows were checked on React 19.3.1 in section 4: the `propTypes` check did not fire, the function with `defaultProps` got `undefined`, and the class got its default value. PropTypes were marked as outdated as far back as April 2017, in React 15.5. To move old code to TypeScript there is an automatic converter: `npx codemod@latest react/prop-types-typescript` ([the upgrade guide to React 19](https://react.dev/blog/2024/04/25/react-19-upgrade-guide)).

### An important boundary: types do not check data from outside

TypeScript and JSDoc check the text of the program, not the data that comes while it runs. The answer of a server or of the AI chef on Gemini may come in an unexpected form — you ran into this when you parsed the model’s answers in your homework. Such data is checked by code before it is passed into props: by hand or with a validation library like Zod.
