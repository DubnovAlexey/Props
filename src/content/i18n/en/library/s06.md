A component gets props from outside and only reads them, while it keeps state itself and can change it. The state of one component very often becomes the props of its children.

### In simple words

The React documentation compares props to the arguments of a function, and state to the memory of a component. An analogy from life: state is your own fridge, you put food in and take it out yourself.

Props are a note from a neighbour: “take the milk”. You can read it and do what it says, but rewriting it makes no sense: the neighbour keeps their own copy.

### Terms of the section

| Term | Strict definition | In simple words |
| --- | --- | --- |
| State | Data a component keeps between renders and changes through a setter | The memory of a component |
| Hook | A special React function whose name starts with `use` | A “hook” by which a component catches hold of React’s abilities |
| `useState` | A hook that creates a state variable and a function to change it | “Give me a memory cell and a button to change it” |
| Setter (set function) | A function like `setProducts` that replaces the value of the state and starts a re-render | A button “save the new value and update the screen” |
| Re-render | Calling the component function again with new data | The component was “photographed again” with fresh data |
| Derived value | A value that can be computed from props or state | It is not stored separately but computed on the fly |

### Comparing props and state

| Question | Props | State |
| --- | --- | --- |
| Where they come from | The parent passes them | The component creates it itself with `useState` |
| Who can change them | Only the parent, by passing new values | Only the component itself, through a setter |
| Can you assign directly | No | No: only through the setter |
| What starts a re-render | A re-render of the parent | A setter call with a new value |
| Analogy | The arguments of a function | The memory of a component |
| An example from the fridge | `product` in `ProductCard` | `products` in `App` |

### The same data: state for one, props for another

```jsx
import { useState } from 'react';

function App() {
  // The STATE of App: the list of products lives here
  const [products, setProducts] = useState([
    { id: 1, name: 'Milk', quantity: 2 },
    { id: 2, name: 'Eggs', quantity: 10 },
  ]);

  return (
    <main>
      {/* The state of App becomes the PROPS of the children */}
      <FridgeSummary count={products.length} />
      <ProductList products={products} />
    </main>
  );
}

function FridgeSummary({ count }) {
  // For FridgeSummary count is a prop: we read it and show it
  return <p>Products in the fridge: {count}</p>;
}
```

For `App` the `products` array is state: it created it and can change it through `setProducts`. For `ProductList` the same array is props, which can only be read. The role of the data depends on whose component is looking at it.

### The re-render loop

1. The user presses a button.
2. The handler calls a setter, for example `setProducts(newProducts)`.
3. React remembers the new state and calls the component that owns the state again.
4. The component returns JSX with new values of the props for the children.
5. React calls the children with the new props and updates in the DOM only the places that have changed.

::scheme rerender

The highlighted step is the one that starts the whole loop: without a setter call there will be no new props.

### An important detail: children re-render together with the parent

By default React re-renders all the children together with the parent, even those whose props have not changed. In the test run a child with a constant `label` prop re-rendered after a click on the parent’s button.

Usually this is not a problem: in the DOM React still changes only the real differences. How to skip extra re-renders when they really get in the way is described in section 10.

### A trap: copying a prop into state

```jsx
// BAD: the state “remembers” the prop only on the first render
function ProductCard({ quantity }) {
  const [qty, setQty] = useState(quantity);
  return <p>{qty} pcs</p>;
}
```

The argument of `useState(quantity)` is used only once, on the first render. In the test run the parent first passed `quantity={2}`, then `quantity={1}`. The prop became 1, but 2 stayed on the screen.

```jsx
// GOOD: we read the prop directly and compute the derived value during render
function ProductCard({ quantity }) {
  const isRunningOut = quantity <= 1; // recomputed on every render
  return <p>{quantity} pcs{isRunningOut ? ' — time to buy more' : ''}</p>;
}

// If it is exactly the INITIAL value that you need, say so in the name of the prop
function QuantityEditor({ initialQuantity }) {
  const [quantity, setQuantity] = useState(initialQuantity);
  // from here on the component manages quantity itself and ignores new initialQuantity values
  return <input type="number" value={quantity} onChange={(e) => setQuantity(Number(e.target.value))} />;
}
```

The prefix `initial` honestly warns whoever uses the component: values passed later will not be taken into account.

### Where to keep data: three questions

1. Can the value be computed from props or other state? If yes, do not store it — compute it during render.
2. Does it change over time and is it needed by only one component? If yes, it is the state of that component.
3. Is it needed by several components? If yes, keep it in their common parent and pass it to the children in props. This is lifting state up from section 7.
