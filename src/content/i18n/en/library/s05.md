Data in React flows only from top to bottom, from the parent to the children, and a child does not change its props. Thanks to these two rules any value on the screen can be traced: it is enough to walk up the component tree.

### In simple words

Imagine the plumbing of a block of flats. Water comes from a tank on the roof and runs down the pipes to every floor. A tenant on the fifth floor uses the water but cannot pump it back into the tank.

If a tenant needs something changed, they call the building manager. In React that is calling a function the parent passed to the child in props (section 7). The tank on the roof is the **state** of the parent, the pipes are the props.

### Terms of the section

| Term | Strict definition | In simple words |
| --- | --- | --- |
| One-way data flow | Data is passed only from the parent to the descendants through props | Data flows down the tree like water down the pipes |
| Component tree | A hierarchy in which every component has one parent | A diagram of “who is inside whom”, like a family tree |
| Descendant | Any component lower in the tree: a child, a “grandchild” and so on | Everyone who lives on the floors below |
| Immutability | Data is not changed after it is created; for changes a new object is created | Do not correct the original, make a new copy with the correction |
| Mutation | Changing an existing object or array in place | Correcting an entry right in the original document |
| Read-only | A value can be read but cannot be assigned a new one | A document under glass: you may look but not correct |
| Pure function | Gives the same result for the same input and changes nothing outside | A calculator: for 2 + 2 it always answers 4 and touches nothing around |
| Side effect | Any action of a function other than returning a result | The function “did something else”: changed an outside variable or sent a request |

### Why props must not be changed: an experiment

```jsx
function ProductCard(props) {
  props.quantity = props.quantity - 1; // A MISTAKE: we try to change someone else’s data
  return <p>{props.name}: {props.quantity}</p>;
}

<ProductCard name="Milk" quantity={2} />
```

| Build mode | What happened in the test run |
| --- | --- |
| Development | The error “TypeError: Cannot assign to read only property 'quantity' of object” |
| Production | No error, “Milk: 1” on the screen. But only the temporary props object of this render changed: the parent’s data is the same |

In development mode React freezes the props object (`Object.freeze`) so that such mistakes catch the eye at once. In production the freezing is turned off for the sake of speed, so the mistake becomes silent. A silent mistake is more dangerous than a loud one.

### A trap: the freezing is shallow

```jsx
const milk = { id: 1, name: 'Milk', quantity: 2 }; // the object belongs to the parent

function ProductCard({ product }) {
  product.quantity -= 1; // there will be NO error: only the props object itself is frozen
  return <p>{product.name}: {product.quantity}</p>;
}

<ProductCard product={milk} />
// After the render milk.quantity === 1 — the parent’s object is spoiled
```

`Object.freeze` freezes only the top level. The `product` object inside the props stays changeable, and the mutation goes through without a single warning. React learns nothing about it and does not re-render the other places where this product is shown. Checked by running it in both modes.

### The right way: “change a prop” means “ask the owner of the data”

```jsx
import { useState } from 'react';

// The child changes nothing itself — it only reports a wish
function ProductCard({ product, onEat }) {
  return (
    <div>
      <p>{product.name}: {product.quantity} pcs</p>
      <button onClick={() => onEat(product.id)}>Eat one</button>
    </div>
  );
}

// The parent is the owner of the data: it creates a NEW array and a NEW object
function Fridge() {
  const [products, setProducts] = useState([
    { id: 1, name: 'Milk', quantity: 2 },
    { id: 2, name: 'Eggs', quantity: 10 },
  ]);

  function handleEat(id) {
    setProducts(
      products.map((p) =>
        p.id === id ? { ...p, quantity: p.quantity - 1 } : p // a copy with a correction instead of a mutation
      )
    );
  }

  return products.map((p) => (
    <ProductCard key={p.id} product={p} onEat={handleEat} />
  ));
}
```

Step by step:

1. `ProductCard` does not touch `product`. It calls `onEat(product.id)` — it “calls the manager”.
2. `Fridge` creates a new array with `map` and a new object with `{ ...p, quantity: ... }`. The old data stays untouched.
3. `setProducts` tells React about the new state. React re-renders `Fridge`, and all the cards get fresh props.

### A component must be pure

React counts on a component behaving like a formula: the same props give the same JSX. During render a component must not change anything that existed before it was called ([the React documentation](https://react.dev/learn/keeping-components-pure)).

```jsx
let renderedCards = 0; // a variable outside the component

// BAD: the component changes an outside variable during render
function ProductCard({ name }) {
  renderedCards = renderedCards + 1; // a side effect
  return <p>No. {renderedCards}: {name}</p>;
}
```

The numbers in such a list depend on how many times React called the function. In development mode inside `<StrictMode>` React deliberately calls components twice to make such mistakes visible. The numbers start “jumping”.

```jsx
// GOOD: everything needed comes in the props
function ProductCard({ name, position }) {
  return <p>No. {position}: {name}</p>;
}

// The parent computes the number from the index in the array
{products.map((p, i) => (
  <ProductCard key={p.id} name={p.name} position={i + 1} />
))}
```

### Props are a snapshot

The React documentation calls props “snapshots in time”: every render gets its own new version of the props ([source](https://react.dev/learn/passing-props-to-a-component)). In simple words: every render is a new photograph. The old photograph is not redrawn — a new one is taken.

If the parent first passed `quantity={2}` and then `quantity={1}`, the first props object does not change. React creates a second object and calls the component again.
