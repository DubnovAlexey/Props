A child cannot change the parent’s data, but it can tell the parent about an event. For this the parent passes a function in the props, and the child calls it at the right moment. In short: data goes down, events go up.

### In simple words

The parent gives the child a remote control with one button. The child does not know what exactly the button does: it presses it at the right moment and reports the details, for example “delete product number 7”. What to do with this message is decided by the parent.

### Terms of the section

| Term | Strict definition | In simple words |
| --- | --- | --- |
| Callback | A function passed to another function or component so that it calls it later | “Call me back when something happens”. You have already met callbacks in higher-order functions |
| Event handler | A function React calls in response to a user’s action | The reaction to a click, typing text or submitting a form |
| Event prop | A function prop whose name starts with `on`: `onDelete`, `onSearch` | The channel through which the child tells the parent about an event |
| Lifting state up | Moving state from the children into their nearest common parent | Instead of two fridges in different rooms — one in the shared kitchen |
| Single source of truth | Every value is kept in exactly one place | The data has one owner, the others get it through props |

### The naming convention

| What we name | The rule | Examples |
| --- | --- | --- |
| The function prop the child gets | `on` + the event with a capital letter | `onDelete`, `onSearch`, `onCardPlay` |
| The handler function in the parent | `handle` + the event | `handleDelete`, `handleSearch` |

These names are recommended by the React documentation ([source](https://react.dev/learn/responding-to-events)). Name props after the meaning of the event in the app (`onDelete`), not after the mouse action (`onButtonClick`). Then the same prop can later be called from the keyboard too.

### Example 1. Deleting a product

```jsx
import { useState } from 'react';

// The child: shows a product and REPORTS the wish to delete it
function ProductCard({ product, onDelete }) {
  return (
    <li>
      {product.name} — {product.quantity} pcs
      <button onClick={() => onDelete(product.id)}>Delete</button>
    </li>
  );
}

// The parent: keeps the list and DECIDES what “delete” means
function ProductList() {
  const [products, setProducts] = useState([
    { id: 1, name: 'Milk', quantity: 2 },
    { id: 7, name: 'Eggs', quantity: 10 },
    { id: 9, name: 'Cheese', quantity: 1 },
  ]);

  function handleDelete(id) {
    setProducts(products.filter((p) => p.id !== id)); // a new array without the deleted one
  }

  return (
    <ul>
      {products.map((p) => (
        <ProductCard key={p.id} product={p} onDelete={handleDelete} />
      ))}
    </ul>
  );
}
```

What happens after a click on “Delete” at the eggs:

1. `ProductList` passed the function `handleDelete` in advance under the name `onDelete`.
2. The click starts the arrow function, and it calls `onDelete(7)`.
3. What actually runs is `handleDelete(7)`: the parent creates an array without the eggs and calls `setProducts`.
4. React re-renders the list. In the test run it was “Milk, Eggs, Cheese” before the click and “Milk, Cheese” after it.

### A typical mistake: a call instead of passing

```jsx
<button onClick={onDelete(product.id)}>Delete</button>       // A MISTAKE
<button onClick={() => onDelete(product.id)}>Delete</button> // RIGHT
```

In the first line `onDelete` is called at once, during render. In the test run all three products deleted themselves, without a single click. React warned: “Cannot update a component while rendering a different component”.

The arrow function in the second line postpones the call until the click. The rule is simple: function props are not called during render, they are called only from event handlers.

### Example 2. Lifting state up: searching the fridge

The task: the search field `SearchBar` and the list `ProductList` must know the same query text. They are neighbours, and neighbours cannot pass props to each other directly. The solution: lift the `query` state up into their common parent `FridgePage`.

::diagram lifting

After lifting, both children get the data from one place, and the search field reports the new text through `onQueryChange`.

```jsx
import { useState } from 'react';

// The search field: keeps nothing itself, gets everything from the parent
function SearchBar({ query, onQueryChange }) {
  return (
    <input
      value={query}                                   // the value came from above
      onChange={(e) => onQueryChange(e.target.value)} // the event went up
      placeholder="Find a product"
    />
  );
}

// The list: shows only what it was given
function ProductList({ products }) {
  if (products.length === 0) return <p>Nothing found</p>;
  return (
    <ul>
      {products.map((p) => <li key={p.id}>{p.name}</li>)}
    </ul>
  );
}

// The common parent is the only owner of query
function FridgePage({ products }) {
  const [query, setQuery] = useState('');

  // a derived value: we compute it during render instead of storing it
  const visible = products.filter((p) =>
    p.name.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <section>
      <SearchBar query={query} onQueryChange={setQuery} />
      <ProductList products={visible} />
    </section>
  );
}
```

The result of the test run on the products “Milk”, “Eggs”, “Cheese”:

| Typed into the field | The list showed |
| --- | --- |
| `mil` | Milk |
| `ee` | Cheese |
| `bread` | Nothing found |
| an empty string | Milk, Eggs, Cheese |

The notation `onQueryChange={setQuery}` passes the setter directly, and that is fine. If extra logic is needed later, it will be added to a `handleQueryChange` in the parent, and `SearchBar` will not have to change.

### How to pass data together with an event

- **One argument:** `onDelete(product.id)`.
- **Several values:** one object is handier, for example `onSearch({ username, dish })`. The order does not matter, and the field names explain themselves.
- **Turning a DOM event into data:** the child takes `e.target.value` and gives plain text up. The parent does not need to know that there was an `<input>` inside.
