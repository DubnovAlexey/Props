Prop drilling — это передача пропа через несколько уровней компонентов, которым он сам не нужен. От него есть два лекарства: композиция через `children` и Context, который доставляет значение сразу тем потомкам, кому оно нужно.

### Простыми словами

Prop drilling похож на записку, которую передают через весь класс: каждый ученик передаёт её соседу, не читая. Context похож на объявление по громкой связи: его слышит каждый, кому оно нужно, и никому не приходится работать почтальоном.

### Термины раздела

| Термин | Строгое определение | Простыми словами |
| --- | --- | --- |
| Prop drilling (протаскивание пропсов) | Передача пропа через промежуточные компоненты, которые его только пересылают | Записка, которую передают через весь класс |
| Context (контекст) | Механизм React для передачи значения всем потомкам без явных пропсов | Громкая связь для всего поддерева |
| `createContext` | Функция, которая создаёт объект контекста со значением по умолчанию | Завести «радиостанцию» |
| Провайдер (Provider) | Компонент, который задаёт значение контекста для всего, что внутри него | Передатчик: «вещаю для всех внутри меня» |
| `useContext` и `use` | Хуки, которые читают значение ближайшего провайдера выше по дереву | Приёмник: «настроиться на станцию» |
| Глобальное состояние | Данные, нужные многим частям приложения сразу | Общая доска объявлений |

### Проблема на примере: роль пользователя в холодильнике

В «Умном холодильнике» есть роли ADMIN, USER и GUEST. Кнопку «Удалить» должен видеть только администратор, а решает это карточка продукта глубоко внизу дерева.

```jsx
function App() {
  const user = { name: 'Алексей', role: 'ADMIN' };
  return <FridgePage user={user} products={products} />;
}

function FridgePage({ user, products }) {
  // FridgePage роль не нужна — он только пересылает user дальше
  return <ProductList user={user} products={products} />;
}

function ProductList({ user, products }) {
  // и ProductList тоже только пересылает
  return <ul>{products.map((p) => <ProductCard key={p.id} product={p} user={user} />)}</ul>;
}

function ProductCard({ product, user }) {
  const canDelete = user.role === 'ADMIN'; // и только здесь user наконец нужен
  return <li>{product.name}{canDelete && <button>Удалить</button>}</li>;
}
```

Чем это плохо:

- Промежуточные компоненты знают о данных, которые им не нужны, и их труднее переиспользовать.
- Новое поле для карточки заставляет править все уровни по пути.
- Чем глубже дерево, тем длиннее цепочка пересылки.

::diagram drilling

Провайдер делает `user` доступным всему поддереву: `ProductCard` читает его через `useContext`, а промежуточным компонентам больше не нужно передавать его по цепочке.

### Лекарство 1: композиция

Документация React советует сначала попробовать обычные пропсы или передачу JSX через `children` и лишь потом браться за контекст ([источник](https://react.dev/learn/passing-data-deeply-with-context)). Если `FridgePage` — просто рамка страницы, пусть она принимает содержимое, а список создаст `App`, у которого уже есть `user`:

```jsx
function App() {
  const user = { name: 'Алексей', role: 'ADMIN' };
  return (
    <FridgePage title="Мой холодильник">
      <ProductList user={user} products={products} /> {/* создаём там, где данные уже есть */}
    </FridgePage>
  );
}

// Теперь FridgePage ничего не знает о пользователе
function FridgePage({ title, children }) {
  return (
    <section>
      <h1>{title}</h1>
      {children}
    </section>
  );
}
```

Один лишний уровень пересылки исчез. Часто этого уже достаточно.

### Лекарство 2: Context

```jsx
import { createContext, useContext, useState } from 'react';

// 1. Создаём контекст. Значение по умолчанию — гость, как в правилах вашего приложения
export const UserContext = createContext({ name: 'Гость', role: 'GUEST' });

// 2. Провайдер: всё, что внутри <UserContext>, видит user
function App() {
  const [user] = useState({ name: 'Алексей', role: 'ADMIN' });
  return (
    <UserContext value={user}>
      <FridgePage products={products} /> {/* user больше не передаём */}
    </UserContext>
  );
}

function FridgePage({ products }) {
  return <ProductList products={products} />;
}

function ProductList({ products }) {
  return <ul>{products.map((p) => <ProductCard key={p.id} product={p} />)}</ul>;
}

// 3. Потребитель: читает значение напрямую, минуя промежуточные уровни
function ProductCard({ product }) {
  const user = useContext(UserContext);
  const canDelete = user.role === 'ADMIN';
  return <li>{product.name}{canDelete && <button>Удалить</button>}</li>;
}
```

Что показал проверочный запуск на React 19.3.1:

| Ситуация | Результат |
| --- | --- |
| `<UserContext value={user}>` с ролью ADMIN | У каждого продукта есть кнопка «Удалить» |
| Провайдера выше нет | Работает значение по умолчанию GUEST, кнопок нет |
| Старая запись `<UserContext.Provider value={…}>` | Тоже работает |
| Два вложенных провайдера | Компонент читает ближайший сверху |
| `use(UserContext)` вместо `useContext` | Работает так же |

Запись `<UserContext value={…}>` без `.Provider` появилась в React 19. В статьях и старом коде вы чаще увидите `.Provider` — оба варианта делают одно и то же.

### Когда что выбирать

| Ситуация | Инструмент |
| --- | --- |
| Данные нужны ребёнку или внуку | Обычные пропсы |
| Промежуточные компоненты — просто рамки и раскладки | Композиция через `children` |
| Значение нужно многим компонентам на разных уровнях: тема, язык, текущий пользователь | Context |
| Большое общее состояние, которое часто меняется | Context + `useReducer` или отдельная библиотека состояния |

### Осторожности с Context

- Все компоненты, которые читают контекст, перерисуются при смене его значения. `memo` от этого не спасает.
- Новый объект в `value` на каждом рендере заставит перерисоваться всех читателей. Храните значение в состоянии или оборачивайте в `useMemo`, как в разделе 10.
- Контекст делает поток данных менее заметным: по пропсам компонента уже не видно, от чего он зависит. Поэтому контекст — инструмент для по-настоящему общих данных, а не замена любым пропсам.
